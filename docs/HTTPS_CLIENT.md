# LocoRoco: временная шкала ввода и display, 0.30

## Текущее состояние и назначение

16 октября 2026 года. 0.29 проверена на PSP: 7161 вызов метода ввода за120с,
преимущественно60–61/с; слот восстановлен, stop/unload/control-free успешны.
Владелец подтвердил обычную START-паузу и нормальную работу управления и
продолжения. Повтор0.29 не нужен. Объект0x0A7B2E8C находился вне разрешённого
диапазона: его поля не читались, FFFFFFFF в журнале — отсутствие данных.
Ожидание остановки опроса на START-паузе было неверным: это пауза внутри игры,
не остановка эмуляции/консоли.

0.30 через прежний единственный слот089B4EE4 наблюдает время, VCount и
метаданные текущего framebuffer до/после оригинального метода08842D90.
Пиксели/VRAM и объект игры не читаются. Используются только GetVcount и
GetFrameBuf(IMMEDIATE); SetFrameBuf, GE и display interrupts не перехватываются.
В игровом потоке нет файлового I/O, выделений памяти и дополнительных ожиданий.
Есть неблокирующая попытка захвата маленькой сводки; пропуски считаются явно.
Длительность оригинального вызова измеряется вместе с частью измерительного
кода, это не точный профилировщик и не измерение общей нагрузки плагина.

Один запуск: сохрани журналы0.29, замени только два PRX из
`PSP_RA_HTTPS_v0.30.zip`, сохрани auth.txt/profile.txt, профиль2 и +16MiB.
Полностью перезапусти PSP. Войди в уровень; играй30с, START-пауза30с,
продолжение30с. Через минимум150с от запуска игры выйди через HOME.
Передай два client-журнала и опиши поведение. При сбое не повторяй.
Wi-Fi не нужен; auth/profile не читаются, аккаунта/HTTP/rc_client в ELF нет,
do_frame/начисления выключены. На PSP0.30 ещё не проверена.

## Как читать результат 0.30

- `TIMELINE`: накопительные captured/missed, duplicate (несколько наблюдений
  до вызова в одном VCount), skipped (пропущенные VCount между наблюдениями),
  resets (неожиданный ход счётчика назад), fb_changes (изменения адреса/stride/
  format между наблюдениями до вызова), errors (ошибка GetFrameBuf), crossed
  (смена VCount между наблюдениями до/после), максимумы длительности/интервала.
  delta — разница входов в обёртку; captured обновляется после оригинала,
  поэтому на границе секунд числа могут временно различаться.
- До4 `TRACE` на секундную выгрузку: времена/VCount/адреса буфера до/после.
  Сводка учитывает все захваченные вызовы; подробные TRACE — только выборка.
- Журнал user ограничен128КиБ, окно наблюдения120с после установки (~10с
  после старта игры). Времена32бит в микросекундах; разности учитывают wrap.
- Метаданные читаются последовательными syscall, не атомарным snapshot.
  Смена адреса буфера не доказывает обновление картинки: двойная смена между
  опросами может остаться незамеченной, отрисовка может идти в том же буфере.
  Это корреляция с display, не журнал всех подач и не эквивалент PPSSPP flip.

## Восстановление и срок жизни

Прежние точные проверки слота и инструкции цикла сохранены. После завершения
наблюдения kernel восстанавливает089B4EE4=08842D90. Но маленький user PRX,
его завершённый worker и control намеренно удерживаются до выхода из игры:
`RUNTIME_PROBE_RETAIN user=RESIDENT control=RESIDENT`. Никакая конечная задержка
с active=0 не доказывает, что другой поток не сохранил адрес обёртки до входа.
Поэтому0.30 не заявляет полную выгрузку/возврат этих ресурсов в процессе игры.
Это исправляет риск lifecycle в0.29. При чужом значении слота восстановление
отказывается писать, модуль и control также удерживаются.

Исходники/выводы PPSSPP — [PPSSPP_FRAME_AUDIT.md](PPSSPP_FRAME_AUDIT.md).
Не расширяем чтение за [08804000,093FB580);0979E4AC остаётся запрещённым.

# LocoRoco: runtime-проверка метода ввода, 0.29

## Назначение

0.28 проверена на PSP и завершилась без ошибок за 22,126с. Установленные
PRX совпали с пакетом. Токен не читался, запросов/кадров/начислений не было,
ресурсы очищены. Статика подтвердила цикл08841788→08844440→повтор:
08841788 обходит объекты и вызывает table+0x14, а08844440 обрабатывает
очередь событий. Последняя функция не является ожиданием кадра.

08841880 устанавливает бит0x02 при a0=1 и снимает при a0=0 для объектов
в заданном диапазоне priority. Найдены шесть прямых callers: 0884A768
передаёт вычисляемое значение; 08863D8C,08933A9C,08959E50 снимают бит;
08933BA4 и08959F84 устанавливают. Это механизм приостановки групп объектов,
но его связь с пользовательской паузой ещё не доказана. Повторять0.28 не нужно.

0.29 измеряет реальное выполнение метода ввода08842D90. Kernel после точной
проверки таблицы089B4ED0 и инструкции цикла временно заменяет только слот
089B4EE4 на адрес обёртки в загруженном RAClientUser. Обёртка считает вызовы,
запоминает объект и всегда вызывает исходный08842D90. Раз в секунду user
записывает delta, state+8, flags+0x0A и priority+0x0C. Все чтения проверяются
по карте загруженных сегментов. Через120с слот возвращается к08842D90;
модуль выдерживается минимум100мс и не выгружается при активной обёртке или
чужом значении слота.

В user ELF отсутствуют rc_client, HTTP, Wi-Fi, операции с токеном и controller
imports. `auth.txt` и `profile.txt` не читаются, сеть не запускается,
`rc_client_do_frame` и начисления отсутствуют. Wi-Fi не нужен. Единственная
временная запись — четырёхбайтовый слот089B4EE4 внутри разрешённого сегмента.

## Один запуск 0.29

1. Сохрани журналы0.28. Из `PSP_RA_HTTPS_v0.29.zip` замени только
   `RAClientBootstrap.prx` и `RAClientUser.prx` в
   `ms0:/seplugins/RAClientLite/`. `auth.txt` и `profile.txt` не заменяй.
   Оставь профиль2 и Extra Memory +16MiB.
2. Полностью перезапусти PSP и запусти LocoRoco USA UCUS98662. Как можно
   быстрее войди в уровень, поиграй около30с, поставь игру на обычную паузу
   кнопкой START примерно на30с, затем продолжи играть ещё30с.
3. Подожди не менее двух минут после запуска игры, выйди через HOME и передай
   `client-bootstrap.log`, `client-user.log` и кратко сообщи, работали ли
   управление, пауза и продолжение. При зависании или сбое тест не повторяй.
4. После сеанса отключи пробу. Успешный bootstrap-журнал должен содержать
   `RUNTIME_PROBE_INSTALL`, затем `RUNTIME_PROBE_RESTORE ... value=0x08842D90
   active=0 ... result=0` и итоговую очистку без ошибок.

`RUNTIME_SAMPLE delta` показывает число вызовов метода за секунду. Нулевой
delta при flags=0x2 во время паузы и возврат ненулевого delta после продолжения
будут прямым свидетельством работы объектного блокиратора. Даже стабильные
~60 вызовов/с ещё не доказывают игровой кадр без результата паузы и проверки
поведения игры. До проверки на PSP binding остаётся UNPROVEN.

- GAME_PAUSE_GUARD: точные инструкции по08844440/08842CA0/08842CA8/

  внутрь. Косвенные вызовы не обходятся. Никакие указатели не исполняются.
- GAME_PAUSE_EDGE: до64 переходов, operation2=J,3=JAL; total_edges считает

- GAME_PAUSE_CALLERS/CALL: полный проход text для прямых J/JAL к

## Подготовка аккаунта на компьютере

Пароль или токен в чат не передавай. Web API key для входа не нужен.
Утилита использует официальный `login2` (тот же запрос, что закреплённый

скрыто и не записывается в файл; ответы сервера и исключения не печатаются.
При отсутствии безопасного интерактивного ввода утилита откажет.

Для запуска 0.27 сохрани существующий auth.txt. Ниже — только
первичная настройка при его отсутствии. Кабель PSP не требуется: файл можно
создать на компьютере и перенести на карту тем же способом, что PRX.
Открой обычный PowerShell и выполни:

```powershell
& 'C:\Users\itzsy\Documents\ChatGPT\PortableAchievementsSystem\scripts\configure_psp_login.ps1' -TokenPath 'C:\Users\itzsy\Documents\auth.txt'
```

Введи логин и пароль своего RetroAchievements-аккаунта в этом терминале.
Утилита запишет **`C:\Users\itzsy\Documents\auth.txt`** с именем и токеном
сессии. Перенеси файл в **`SEPLUGINS\RAClientLite\auth.txt`** на карте PSP.
Если карта доступна как D:, можно сразу указать
`-TokenPath 'D:\SEPLUGINS\RAClientLite\auth.txt'`.
Действующий Python 3.12.14 найден в локальном runtime Codex;
установка не нужна. На другом компьютере wrapper принимает
`-PythonExecutable 'C:\путь\python.exe'`. Если буква диска другая, укажи
`-TokenPath 'E:\SEPLUGINS\RAClientLite\auth.txt'`.

`auth.txt` — **секретный незашифрованный файл на Memory Stick**. Он не входит
в архив/репозиторий, не является защищённым хранилищем и не должен попадать
в отправляемые папки, скриншоты или резервные копии для диагностики.
Существующий файл не перезаписывается. Проба не изменяет его после входа.

Для выхода закрой игру и удали auth.txt с карты памяти и оставшуюся копию
на компьютере. Если карта доступна как D:, используй:

```powershell
& 'C:\Users\itzsy\Documents\ChatGPT\PortableAchievementsSystem\scripts\configure_psp_login.ps1' -Logout
```

Команда удаляет только распознанный `auth.txt` этого клиента. Это локальный
выход, а не обещание серверного отзыва токена на других устройствах.
Для повторного входа сначала выполни выход, затем запусти настройку заново.

Следующий сценарий сохранён для истории. В **0.24 его не выполнять**:
четыре нажатия и наблюдение счётчика удалены из активной пробы.

## Установка и один запуск

1. Сохрани предыдущие два лога. Оставь **Use Extra Memory → +16MiB**.
2. Из **PSP_RA_HTTPS_v0.23.zip** замени **оба PRX** в
   `ms0:/seplugins/RAClientLite/`: RAClientBootstrap.prx и RAClientUser.prx.
   Сохрани свои **auth.txt и profile.txt (профиль 2)**.
3. Включи Wi-Fi, отключи остальные RA-пробы. Единственная запись:

   ```text
   UCUS98662, ms0:/seplugins/RAClientLite/RAClientBootstrap.prx, on
   ```

4. Полностью перезапусти PSP. Запусти тот же LocoRoco и подожди минуту.
   Затем выполни четыре коротких нажатия **L+R+SELECT**, каждый раз
   отпуская кнопки минимум на секунду:

   - Начни обычный этап и нажми сочетание **первый раз**. Играй 30 секунд.
   - Открой настоящую внутриигровую паузу, затем нажми сочетание
     **второй раз**. Оставайся на паузе 30 секунд.
   - Сними паузу, нажми сочетание **третий раз** и играй ещё 30 секунд.
   - Нажми сочетание **четвёртый раз** — оно завершает наблюдение.

   **Проходить Kulche до конца не требуется.** Используй паузу игры,
   не HOME, сон или меню CFW. SELECT может действовать и на саму игру:
   сочетание не перехватывается. Если оно снимает паузу или меняет меню,
   сообщи об этом: отметка не доказывает состояние паузы.
   После загрузки набора отведено 4 минуты. При сбое не повторяй вслепую.
5. После четвёртой метки подожди 10 секунд, выйди через HOME и передай
   **только client-bootstrap.log и client-user.log**. Сообщи поведение игры,
   были ли четыре нажатия, как открывал паузу и оставалась ли она активной.
   Не передавай всю папку: она содержит секретный auth.txt.
   После проверки отключи запись пробы.

## Что ищем в логах

- client_version=0.23 в обоих журналах; login, набор и cleanup без ошибок.
- `GAME_CANDIDATE_CODE result=0`: количество прямых вызовов функции.
  Сохраняются до 8 окон по 33 инструкции и до 64 слов самой функции.
  Поиск J/JAL не обнаруживает косвенные вызовы и не доказывает выполнение.
- `FRAME_CANDIDATE_BEGIN ... signature=1` после набора.
- `FRAME_CANDIDATE_MARK index=1..4`: метки владельца. Это подписи
  фаз, а не автоматическое распознавание активности/паузы.
- `FRAME_CANDIDATE_WINDOW phase=0..3`: фаза 0 до первой метки,
  1 — отмеченная игра, 2 — отмеченная пауза, 3 — после снятия паузы.
  Окна по 10 секунд; крайние окна содержат переход между состояниями.
  Сравнивать прежде всего полные окна внутри каждой фазы.
- increments — сумма наблюдавшихся приращений, changes — число чтений
  с изменением. Ни одно из этих чисел пока не называется игровыми кадрами.
  vblanks/buffer_changes — независимые наблюдения вывода, не логики.
- counter_gaps/display_gaps >0 означают разрыв >250 мс или откат времени;
  приращение через такой разрыв не считается. discontinuities — скачок
  >1024 за опрос либо переполнение суммы; это диагностический предел,
  не измеренный лимит FPS. Короткое чтение — ошибка, а не нулевое значение.
- Если счётчик продолжает идти на настоящей паузе, он не подходит как
  готовый источник кадров логики без отдельного определения паузы.
  Если останавливается, это полезный кандидат, но ещё нужно доказать
  один вызов на обновление логики и момент безопасного чтения памяти.
- `FRAME_CANDIDATE_DONE marks=4 completed=1 ... binding=UNPROVEN`:
  сценарий собран, синхронизация и достижение этим не подтверждаются.
- -35414 — не получены четыре метки за 4 минуты; -35415 — несовпадение
  сигнатуры или ошибка её чтения; -35416 — ошибка чтения счётчика.
  Передать логи при любом исходе. Старый TARGET_STATE_REJECT для Delta
  ожидается и больше не прекращает наблюдение счётчика.

## Границы пробы

Тот же закреплённый rcheevos v12.5.0 и PSPDEV из dependencies.lock.json.
Доступ только к подтверждённым сегментам игры; RA 0x0179E4AC запрещён.
Опрос около 5 мс выполняется в диагностическом потоке, не в игровом.
Счётчик читается одним выровненным volatile uint32_t после проверки адреса
тем же адаптером диапазонов. Это не делает снимок остальной памяти
атомарным и не доказывает границу кадра; проба не используется для Delta.
История rcheevos, события и открытия не продвигаются. Старые .dat
не читаются и не отправляются. Сетевой транспорт и очистка прежние.
Новые запросы к аккаунту, помимо прежних login/набора, не добавлены.
Не гарантируются очередь после выключения, стабильность FPS и полный
онлайн-клиент: измерения и проверка на настоящей PSP ещё впереди.


## Историческая справка 0.19–0.22

Следующие разделы описывают прежние сборки и сохраняют принятые решения.
Для запуска 0.23 применяются сценарий и коды результатов выше; ручная
проверка условия из старых разделов в 0.23 не выполняется.

## Ограничения ручной проверки 0.22

Официальный parser rcheevos v12.5.0 разбирает отдельную копию выбранного
определения (до 4096 символов / 32 КиБ). Разрешены только прямые целые
чтения и сравнения STANDARD/PAUSE_IF без счётчиков попаданий. Delta/prior,
indirect, hit targets, measured/reset, арифметика, float и иные формы
отклоняются целиком; максимум 16 ссылок, 128 условий, 16 альтернатив.
Это сознательно узкий фильтр, не заявление о поддержке всех stateless-форм.

На нажатие выполняются два прохода разрешённых чтений; различие/ошибка
отменяет проверку. Два совпавших прохода **не доказывают атомарный снимок**
игрового состояния. Затем private trigger сбрасывается и проверяется
официальным rc_test_trigger по сохранённым байтам. История между проверками
не накапливается; требуется наблюдавшийся false перед true. Статистика
matched не является событием rc_client, popup, сохранением или зачётом.

Определение перехватывается без изменения ответа в owner callback
post_process_game_sets_response внутреннего ABI закреплённого rcheevos.
Принимаются точные Game ID 10523 / console 41 / core ID 397986, ровно одно
совпадение. Буфер живёт до закрытия сессии. Сеть остаётся в своём потоке,
rc_client обслуживается idle; frames/earned=0. Новых запросов, логов значений
памяти, определений, локальных профилей и очереди открытий нет.

Полный автоматический движок всё ещё требует доказанной точки игрового
кадра и паузы. Тест одного состояния этого требования не заменяет.
Наблюдение display сохраняется как справочное, отчёт раз в 30 секунд;
проверка памяти и стоп-условий bootstrap остаётся ежесекундной,
регулярный лог после 20-й секунды — раз в 5 секунд (лимит 64 КиБ).

## Целевой анализ 0.20

Локальный оригинальный EBOOT имеет magic `~PSP`, а не готовый ELF.
Не подменяем этим файлом загруженные инструкции или официальный RA-хеш.
Вместо нового опроса VBlank kernel один раз перед release читает таблицу
импортов и text именно проверенного модуля LocoRoco. Каждое чтение
целиком ограничено сегментом; код игры и import stubs не изменяются.

Распознаются только короткие точные имена sceDisplay/sceCtrl/sceGe_user
и семь NID из закреплённого PSPSDK: SetFrameBuf, WaitVblankStart/CB,
Peek/ReadBufferPositive, GeListSync/GeDrawSync. Для найденных stub адресов
сканируются прямые MIPS J/JAL в text. Максимумы: text 4 МиБ,
таблицы 16 КиБ / 128 библиотек / 4096 функций, 8 нужных импортов,
24 сохранённые точки вызова. total_calls показывает также отброшенные
из-за лимита совпадения. Повреждённые указатели/размеры и неудачные чтения
останавливают анализ, но не расширяют доступ к памяти.

`GAME_IMPORT` и `GAME_CALL` содержат NID/адреса. `CODE <pc> <word>` —
до 33 слов инструкций вокруг каждой из 24 точек: максимум 3168 байт кода,
не полный executable. Это ограниченные фрагменты игры для локального
анализа; секретные данные клиента и значения игрового состояния туда
не входят. Они появляются только в bootstrap log, а не в ZIP.
Вызовы через регистры/обёртки и фактическое исполнение этим проходом
не устанавливаются; совпадение J/JAL само по себе не доказывает кадр.
Скрипт `scripts/analyze_game_code.py` на компьютере расшифровывает небольшой
набор MIPS-инструкций из этих записей, неизвестные оставляет как .word.
Он не обращается к сети/аккаунту и читает только явно переданный
client-bootstrap.log размером до 64 КиБ.

`GAME_BLOCK` на метках 10 и 60 вызывает sceKernelQueryMemoryInfo для
0x0979E4AC. Логирует native result, partition UID, block UID и совпадение
с mem_id модуля LocoRoco/control. Partition UID нельзя автоматически
считать номером раздела 2. rc=0 с block_uid=-1 не подтверждает выделение.
Даже совпадение с блоком игры не доказывает смысл адреса как состояния
достижения. Новых разрешённых диапазонов нет, `read=DENIED` сохранён.
ABI сверён с PSPSDK export и первичным
[uOFW memory.c](https://github.com/uofw/uofw/blob/28306bb5bd4fcdcc0c1d469bf1f3bdb885dde3e9/src/kd/sysmem/memory.c#L1096).
Это справочник ABI, не версия прошивки владельца; код uOFW не включён.

Result анализа: -1 входные границы, -2 import metadata/read,
-3 лимит нужных импортов, -4 чтение text. Нулевой result означает
успешный статический проход, не найденный/проверенный игровой цикл.
Анализатор кода не ставит хуки, не меняет защиту и не выполняет условия.

## Чтение памяти и источник кадров: история 0.19

Перед release на метке 10 kernel запрашивает metadata именно LocoRoco,
проверяет user-модуль, 1–4 непересекающихся сегмента и покрытие text.
Каждый сегмент должен целиком лежать в `0x08800000..0x09FFFFFF`.
Карта публикуется до request_allowed с барьером памяти; user копирует её
после ожидания release. Kernel каждую секунду перепроверяет UID/сегменты;
при смене/ошибке запускается остановка, живой worker сохраняет control.

RA-адрес преобразуется общим адаптером закреплённой карты PSP:
`PSP = 0x08000000 + RA`. Полное чтение должно войти в один разрешённый
сегмент. Нулевые размеры, переполнение, kernel/aliases, extra RAM, разрывы
и динамический heap вне сегментов отвергаются **до разыменования**.
Код игры, её таблицы и данные не изменяются. При stop чтения прекращаются.
Чтение нескольких байт не является согласованным снимком игрового кадра.

`GAME_READ` — статистика callback проверки адресов при загрузке rc_client.
`GAME_READ_ACCEPT`/`GAME_READ_DENY` показывают первые 16 различных пар
RA-адрес/размер каждого вида. Это не дамп: значения памяти не выводятся.
Первые 16 принятых чтений размером 1–4 байта повторяются при отчёте окна;
лог содержит лишь количество изменившихся адресов. Эти чтения не выполняют
условия rc_client и не расширяют разрешённые диапазоны.

Наблюдение каждые 5 мс читает `sceDisplayGetVcount` и
`sceDisplayGetFrameBuf(IMMEDIATE)`, не читая видеопамять. Отчёт каждые
5 секунд или при смене ручной фазы: elapsed/window, vblank,
observed_buffer_changes, polls, display_errors, gaps, sampled/changed_addresses.
Разрыв опроса больше 250 мс сбрасывает базу сравнения буферов и отмечается
gaps. Ошибка/NULL framebuffer тоже сбрасывает базу. Наблюдаемые смены могут
быть пропущены между опросами; повторное использование буфера не замечается.

Ручная фаза — метка владельца, **не автоматическое распознавание паузы**.
Счётчики экрана, даже совпадающие с ожидаемыми 30/60 FPS, не доказывают
связь с обновлением логики или точность коротких событий. 0.19 собирает
данные для выбора точки синхронизации; готовой привязки кадров в ней нет.
В игровом потоке нет сетевых операций/новых хуков, `rc_client_idle`
обслуживается владельцем, `do_frame` отсутствует во всех фазах.

## HTTP-приёмник 0.17 и увеличенный бюджет 0.18

Поддерживаются допустимые символы field-name, расширения чанков (включая
quoted-string/escape) и завершающие поля. Неизвестные завершающие поля
проверяются и отбрасываются, не сливаются с заголовками. Content-Length,
Transfer-Encoding и Content-Encoding в trailer отвергаются. Основание —
[RFC 9112 7.1](https://www.rfc-editor.org/rfc/rfc9112.html#section-7.1) и
[RFC 9110 5.6.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-5.6.2).

Лимиты независимы: начальные заголовки 4096 байт, строка до 1022 байт
без CRLF, служебные байты всех чанков 16384, trailers 2048, тело 262144.
Прежде строки размеров чанков ошибочно расходовали 4096 байт заголовков.
Теперь 1500 однобайтовых чанков проходят без расхода header budget.
Разбор ограничен по памяти и времени; gzip/deflate/br и неоднозначное
фреймирование по-прежнему отвергаются. Redirects не выполняются.

После SESSION_HTTP owner пишет HTTP_DIAG с номером ticket. Все строки
error/phase/encoding выбираются из таблиц в коде; имена/значения заголовков,
куки и тело ответа не выводятся. Числовые поля:

- `received`: сколько байтов тела декодировано до отказа; `wire`: сколько
  расшифрованных HTTP-байтов TLS передал приёмнику, включая заголовки/чанки.
- `declared`/`has_length`: значение/наличие Content-Length; при переполнении
  32 бит — UINT32_MAX и `number_overflow=1`, без обёртывания числа.
- `chunked`, `chunks`, `last_chunk`: режим, число непустых чанков и последний
  объявленный размер; `headers`, `trailers`, `chunk_meta`, `line_bytes` —
  счётчики до отказа. `limit=262144` — общий предел тела транспорта и очереди.

HTTP-статус сохраняется сразу после разбора status line, даже если ответ
отклонён. `body_bytes` при отказе остаётся 0: буфер очищен и не отдаётся
rc_client как успешный/частичный ответ. Это не означает пустое тело сервера.
При `has_length=0` величина declared=0 не является объявленным размером.

| Code / HTTP_DIAG error | Значение |
| --- | --- |
| -35202 / body_limit | Тело или объявленный размер чанка превышает буфер |
| -35202 / header_limit, line_limit, chunk_meta_limit, trailer_limit | Исчерпан соответствующий бюджет служебных данных |
| -35205 / status, header_syntax, content_length, number_overflow, framing_conflict, chunk_syntax, trailer_syntax, trailer_framing, crlf, extra_data | Некорректное или неоднозначное HTTP-сообщение |
| -35206 / content_encoding, transfer_encoding | Неподдерживаемая кодировка |
| -35207 / truncated, unauthenticated_close | Усечённое тело или закрытие без TLS close_notify |
| native TLS/BIO code / transport_error | Ошибка TLS/сокета во время приёма; исходный код сохранён |

На timeout/cancel сохраняются уже разобранные счётчики/статус, а code
остаётся -35203/-35204. `error=none` в таком случае не означает успех:
нужны одновременно stage=complete, code=0 и требуемый HTTP/JSON-результат.
Точную причину отказа 0.16 эти изменения задним числом не устанавливают.
В 0.17 превышение лимита доказано. Новый предел 256 КиБ проверен локально;
если реальный ответ больше, он также будет отклонён целиком с диагностикой.

## Ресурсы и жизненный цикл

Ранний init/отложенный Connect из 0.15 сохранён. До загрузки/каждого init
нужно 2 МиБ свободной и достаточно крупного блока; это preflight, не резерв.
**Heap 2 МиБ**, как в 0.16, приобретается до падения свободного запаса
при старте. 0.18 подтвердила разбор настоящего набора и возврат heap.
Пик всех выделений при разборе пока неизвестен; чтение и более длительное
наблюдение 0.19 требуют отдельной проверки на PSP.
Owner и отдельный HTTPS-поток имеют стеки по 32 КиБ, entry — 8 КиБ.
ELF ограничен 320 КиБ, файл PRX — 384 КиБ по измеренной сборке 0.16.
`client_heap` записывает arena/allocated/free_in_arena при раннем старте,
после загрузки набора и после уничтожения клиента; это текущие значения,
не пиковый расход и не размер крупнейшего свободного блока.
Рабочий guard user free — 192 КиБ, largest — 8 КиБ. DDR/CFW/память игры
и приоритеты не изменяются. Размещение в partition 9 не применяется.

Owner единолично вызывает rc_client, разбирает ответы и пишет лог.
HTTPS-поток получает POST через очередь под семафором и возвращает копию
ответа; callback вызывается только при owner tick. Очередь: 2 слота,
POST <=8192, response <=262144, суммарные буферы <=270338 байт
(8192+1+262144+1, общий бюджет двух слотов). Отдельный рабочий
response-буфер 256 КиБ выделяется заранее и очищается после запроса.
Во время копирования одновременно существуют рабочее тело и его копия
в очереди; при разборе добавляются выделения rc_client. Набор LocoRoco
поместился в 0.18 с выключенным чтением; это не гарантия для других наборов.

`SESSION_QUEUE` перед закрытием клиента показывает current/peak этих
буферов, limit, pending/submitted/completed и `last_copy_error`:

| last_copy_error | Значение |
| --- | --- |
| 0 | Последнее копирование успешно |
| 1 | Отмена или истечение срока запроса |
| 2 | Транспорт не передал допустимый HTTP status |
| 3 | Размер тела больше 256 КиБ |
| 4 | Исчерпан общий бюджет буферов очереди |
| 5 | malloc копии ответа вернул NULL |
| 6 | Непустое тело передано с NULL-указателем |

Это причина последней попытки копирования, а не общий итог HTTP/JSON.
Queue peak не включает рабочий буфер, TLS, объекты rc_client и стеки;
он не является пиком всего heap. Содержимое POST/ответов не выводится.

Разрешены только `login2`/`achievementsets` на точном HTTPS endpoint;
award/leaderboard/startsession/ping не проходят через этот транспорт.

На запрос — 30 с с момента постановки в очередь, максимум 4 запроса.
Ранний init/ожидание release — 20 с, затем общий предел хеша/Wi-Fi/сессии —
100 с. После успешной загрузки набора — отдельные 90 с наблюдения + 5 с
запаса; bootstrap ограничен 180 с от старта своего наблюдения. Журналы
ограничены: bootstrap 64 КиБ, user 16 КиБ. Native DNS — 1 с/retry 1;
TCP/TLS poll <=50 мс. Потеря сети, питание,
guard или выход отменяют операцию. Повторной отправки и офлайн-очереди нет.
TLS 1.2 проверяет цепочку, hostname и RTC; redirects/gzip отвергаются.
TLS allocations <=64 КиБ, делят общий heap с клиентом. KIRK seed питает
родительский CTR-DRBG; каждая TLS-сессия получает новые байты из него.
Старый одноразовый seed не переиспользуется между соединениями.
CA — закреплённый GTS Root R4, без отключения проверки сертификатов.

При завершении owner сначала останавливает и проверяет STOPPED/done сетевого
потока, затем закрывает очередь/клиент (logout), освобождает сеть/APCTL и heap.
Если join/очистка неопределённы, объекты и модуль удерживаются с done=0;
живой поток не получает освобождённую память. Семафоры удаляются после их
последнего пользователя. Stop helper bootstrap 0.13 сохранён.
Ожидание queue lock безуспешно продолжать нельзя: при native ошибке поток
останавливается, done не подтверждается и модуль сохраняется.

Основные новые отказы: -35401 queue guard, -35402 лимит запросов,
-35403 публикация ответа, -35404 отсутствующий/повреждённый auth.txt,
-35405 login, -35406 set/ID/console, -35407 join сетевого потока,

Сборка: `scripts/build_client_https.ps1`, закреплённый SDK без сети контейнера.
Локально проверяются официальный rc_client с синтетическим набором,

## Диагностика отказа в 0.22

При eligible=0 следующая строка TARGET_STATE_REJECT показывает первый отказ.
Группа 0 — основная, 1..16 — альтернативы. condition и operand нумеруются
с 1; 0 означает отказ до проверки отдельного условия/операнда.
detail=group_flags означает отказ по агрегатным счётчикам группы:
indirect, hittarget, reset, measured. При таком отказе condition=0.
Другие detail: operand_type/access/combining/size, missing_memref,
memref_type/size, condition_type, operator, required_hits,
refs_limit, conditions_limit, groups_limit. Числовые type/operator/operand_type/
access/size соответствуют enum закреплённого rcheevos v12.5.0.
Для parse/limit/not_found выводится прежняя причина без деталей конструкции.
Полное определение, значения памяти и секреты в эту строку не попадают.
Фильтр допуска, spectator=1, hardcore=0 и запрет do_frame/award сохранены.
