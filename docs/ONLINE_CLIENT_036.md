# 0.36: исправление нестабильного меню

0.35 на PSP открыла меню, но владелец сообщил дёргание и нечитаемый список.
На фото видна нижняя часть панели. Причина по фото не доказана. В коде обнаружены
прямая запись в отображаемый буфер игры и отсутствие согласованного владения
экраном. Статические снимки 0.35 не проверяли эту конкуренцию.

План исправления: собственные двойные буферы 512×272 RGB565; согласованная
пауза в существующем hook; смена готового буфера на VBlank; проверка текущей
и ожидающей ссылки Display перед повторной записью и освобождением памяти.
Потом переносимые проверки жизненного цикла, PSP-сборка, проверка ZIP.
0.36 проверена владельцем PSP: меню стабильно, четыре открытия/закрытия
подтверждены UI_CLOSE restored=1, fault=0. Карточка загрузки всё ещё мигает.
Журналы не содержат финала сессии, штатная очистка по ним не подтверждена.

База: upstream e0cd8a9b3ccf439532b24b4f1faf2cfc8c0198ab;
rcheevos 12.5.0 / 1433173220a7eaede6a9ed7a18e94117be1821e0.
PSPDEV/PSPSDK: закреплённый digest из dependencies.lock.json, GCC 15.2.0.
Исходные переносимые тесты 0.35 перед изменениями — PASS.

## Поведение

L+R+SELECT, удерживать 400 мс. Запрос меню подтверждается игровым callback
после обработки текущего вызова и освобождения engine/queue/timeline locks.
Ожидание предусмотрено только для открытого меню; сетевые операции в игровой
поток не перенесены. Не применяется массовый SuspendThread.
Worker продолжает rc_client_idle, доставку сетевых ответов и обработку ввода.
При закрытии экран освобождается до возобновления callback. Пропущенные кадры
не догоняются. START-пауза игры сама по себе не используется для запрета кадров.

Перед показом меню GE только опрашивается (`sceGeDrawSync(1)`), без блокирующего
ожидания GPU. Отсутствие подтверждения hook, простаивания GE или стабильного
экранного буфера за 1,5 секунды отменяет открытие. Независимый игровой поток
может продолжать работу: если он меняет Display, меню закрывается и пишет
UI_DISPLAY_CONFLICT. Пауза одного hook не объявляется доказательством остановки
всех потоков игры. Это проверяется на конкретной LocoRoco.

Меню строится в невидимом собственном буфере. После cache writeback готовый
буфер передаётся Display с NEXTFRAME. Отображаемый и ещё ожидающий переключения
буфер не перерисовываются. При закрытии восстанавливается предыдущий экран;
переходы HOME/игры сохраняются, если Display уже перешёл к другому владельцу.
Освобождение разрешено только после ухода обеих ссылок Display с наших буферов.
При неясном состоянии память сохраняется, клиент защитно завершается.
Watchdog heartbeat прекращает ожидание игрового callback при зависании worker.

Два буфера занимают 557056 байт в прежнем heap 2 MiB. Heap, границы игровой
памяти, HTTPS и условия достижений не расширяются. При нехватке памяти
подготовка заканчивается ошибкой -35417. Ошибка восстановления: -35419;
отсутствие heartbeat: -35420. Это не обещание измеренного расхода на PSP.

В журнале: UI_PAUSE_REQUEST, UI_OPEN (исходный адрес/stride/формат),
UI_OPEN_ABORT, UI_DISPLAY_CONFLICT, UI_CLOSE restored=1.
Нижние всплывающие карточки пока рисуются в игровом буфере, но после реального
WaitVblankStart и повторного получения его адреса. Это отдельно проверяется на PSP.

## Проверка владельцем

Заменить только оба PRX из нового архива, сохранить свои mode/profile/duration
и auth.txt. Для просмотра уже открытых достижений нужен softcore; spectator
не загружает открытия аккаунта. Не требуется повторное получение достижения.
После полного рестарта запустить LocoRoco, дождаться загрузки набора,
открыть меню на 20–30 секунд, проверить список, фильтры, закрытие и продолжение.
Повторить открытие/закрытие несколько раз. Передать два журнала и результат
по стабильности изображения. Если меню не открылось, журнал должен различить
нехватку памяти, отсутствие паузы, занятый GE и конфликт Display.
Карту, аккаунт и GitHub агент не меняет. Проверка сна/Wi-Fi остаётся отдельной.
